# ConduitMCP 0.11.0 — MCP 2026-07-28 Dual-Era Support

**Date:** 2026-08-07
**Status:** Approved design, pending implementation plan
**Target release:** 0.11.0 (single big-bang release)

## Problem

ConduitMCP implements MCP `2025-11-25` (accepting `2025-06-18` for
compatibility). The current protocol revision is
[`2026-07-28`](https://modelcontextprotocol.io/specification/2026-07-28), the
largest breaking revision MCP has published. It does not extend the existing
model; it removes it. Sessions, the `initialize` handshake, server-initiated
requests, the GET SSE endpoint, `ping`, `logging/setLevel`, and stream
resumability are all gone, and tasks have moved out of core into an extension.

No client fleet has migrated. The library must therefore serve both revisions
from the same endpoint for the foreseeable future.

## Goals

- Full conformance with `2026-07-28` (the **modern** era).
- Unbroken service for `2025-11-25` and `2025-06-18` clients (the **legacy**
  era), on the same endpoint, with no configuration.
- Zero required changes for existing users: a server written against 0.10.x
  compiles and runs on 0.11.0, serves legacy clients exactly as before, and
  gains modern core-method support automatically.
- A clean deletion point for the legacy era in a future release.

## Non-goals

- Client-side implementation of the modern era. `ConduitMcp.Client` is a
  payload-builder helper, not an MCP client, and stays that way.
- Single-use `requestState` redemption (requires server-side storage; the
  spec makes it the implementer's problem and we document it as such).
- Distributed subscription fan-out. The subscription registry is node-local;
  multi-node fan-out is documented as a user-supplied PubSub layer calling the
  public notification API on each node.
- Removing the deprecated HTTP+SSE transport (`sse.ex`). It remains as-is.

## Terminology

Taken from the spec's own
[versioning page](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning):

- **Modern** — `2026-07-28` and later. Version, identity, and capabilities
  travel as per-request `_meta`. Stateless.
- **Legacy** — `2025-11-25` and earlier. Establishes a session via an
  `initialize` handshake.
- **Dual-era** — an implementation serving both. ConduitMCP 0.11.0 is dual-era.

## What changed in 2026-07-28

Nine major changes, all in scope:

1. Protocol-level sessions and `Mcp-Session-Id` removed (SEP-2567).
2. `initialize`/`notifications/initialized` removed; per-request `_meta`
   carries `io.modelcontextprotocol/protocolVersion`,
   `io.modelcontextprotocol/clientInfo`, and
   `io.modelcontextprotocol/clientCapabilities` (SEP-2575).
3. `server/discover` added — servers **MUST** implement it (SEP-2575).
4. HTTP GET endpoint and `resources/subscribe`/`unsubscribe` replaced by
   `subscriptions/listen` (SEP-2575).
5. `ping`, `logging/setLevel`, and `notifications/roots/list_changed` removed;
   log level is per-request `_meta` (SEP-2575).
6. Tasks moved to the `io.modelcontextprotocol/tasks` extension and redesigned
   (SEP-2663).
7. Multi Round-Trip Requests (MRTR) replaces server-initiated requests
   (SEP-2322).
8. All results carry a required `resultType` (SEP-2322).
9. SSE resumability and `Last-Event-ID` removed (SEP-2575).

Plus required `ttlMs`/`cacheScope` cache hints (SEP-2549), mandatory
`Mcp-Method`/`Mcp-Name` headers and `x-mcp-header` (SEP-2243), an error-code
allocation policy renumbering three codes, `resources/read` not-found moving
from `-32002` to `-32602`, OpenTelemetry `_meta` conventions (SEP-414),
deterministic `tools/list` ordering, JSON Schema 2020-12 loosening (SEP-2106),
and OAuth changes (RFC 9207 `iss`, `application_type`, issuer-bound
credentials). Roots, Sampling, Logging, HTTP+SSE, and OAuth DCR are formally
deprecated.

## Decisions

Recorded with the reasoning, so a future reader can tell which constraints are
real and which were preference.

| # | Decision | Reasoning |
|---|---|---|
| D1 | Single big-bang 0.11.0 rather than staged releases | User's call. Buys one coherent cutover instead of six half-migrated intermediate states. Accepted cost: no intermediate release proves any change in the wild. |
| D2 | Dual-era, always on, same endpoint | No client fleet has migrated. Spec explicitly sanctions it. |
| D3 | Era-split handlers over a shared core | Puts the seam exactly where the spec puts it — classification and response shaping. ~70% of behavior (validation, component resolution, auth, telemetry) is era-independent and must not be duplicated. |
| D4 | MRTR via explicit return tuple; library owns state sealing | Truly stateless, matches SEP-2322 one-to-one, keeps handlers plain functions. A suspending-process model would reintroduce sticky routing — the exact thing SEP-2322 exists to eliminate. |
| D5 | Fork tasks into two subsystems | The legacy and extension task shapes differ enough that a superset record would compromise both. Frozen legacy subsystem is trivially deletable later. |
| D6 | `Ext.Tasks` opt-in and marked experimental | The `ext-tasks` repo self-describes as experimental and not official, still tracking SEP-2663, and already conflicts with core on an error code. |
| D7 | Full support for the deprecated trio, marked `@deprecated` | Roots and Sampling remain available as MRTR input requests; per-request Logging remains available. All three carry deprecation markers so users get warning before removal. Elicitation is not deprecated and carries no marker. |
| D8 | Cache hints: global default + per-component override, `"private"` default | Required fields need a default that cannot leak an auth-gated response through a shared intermediary. `"public"` must be deliberate. |
| D9 | Keep `2025-06-18` in `supportedVersions` | Costs one list entry; the legacy path already handles it. |

## Architecture

### Era resolution

Classification happens once, at the transport boundary, and is total:

- **Modern** — `params._meta["io.modelcontextprotocol/protocolVersion"]` is
  present, **or** the method is `server/discover`.
- **Legacy** — everything else, including `initialize` and any request
  carrying `Mcp-Session-Id`.

`server/discover` is era-exempt because a client may call it precisely to
find out which era the server speaks.

The result is `%ConduitMcp.Ctx{}`, threaded through every layer:

```elixir
%ConduitMcp.Ctx{
  era: :modern | :legacy,
  version: String.t(),
  client_info: map() | nil,
  client_capabilities: map(),
  extensions: map(),
  log_level: String.t() | nil,
  principal: term() | nil,
  session: ConduitMcp.Session.t() | nil,  # legacy only
  conn: Plug.Conn.t()
}
```

This replaces the current practice of re-reading values out of `conn.assigns`
at each layer.

### Request flow

```
POST /mcp
  -> ConduitMcp.Era.classify/2
     -> modern:  Plugs.HeaderValidation -> Handler.Modern
     -> legacy:                            Handler.Legacy
       -> Handler.{Tools,Resources,Prompts,Completion}   (era-agnostic core)
         -> Protocol.Modern | Protocol.Legacy            (response shaping)
```

### Handler contract change

`subscriptions/listen` answers a POST with a long-lived SSE stream, so dispatch
can no longer return only a map.

```elixir
@spec dispatch(request :: map(), server_module :: module(), Ctx.t()) ::
        {:reply, map()} | {:stream, ConduitMcp.StreamSpec.t()} | :noreply
```

`ConduitMcp.Handler.handle_request/3` keeps its existing signature and
map-returning contract, implemented as a wrapper over `dispatch/3`. Manual-mode
users (see `guides/manual_mode.md`) are unaffected. A `{:stream, _}` can only
arise from `subscriptions/listen`, which `handle_request/3` rejects with
`-32601`.

### Module changes

**New:**

| Module | Responsibility |
|---|---|
| `ConduitMcp.Ctx` | Per-request context struct |
| `ConduitMcp.Era` | Request classification |
| `ConduitMcp.Handler.Modern` | Modern routing table |
| `ConduitMcp.Handler.Legacy` | Legacy routing table |
| `ConduitMcp.Handler.{Tools,Resources,Prompts,Completion}` | Era-agnostic method bodies |
| `ConduitMcp.Protocol.Modern` | `resultType`, cache hints, `serverInfo` `_meta`, modern error codes |
| `ConduitMcp.Protocol.Legacy` | Current response shaping, extracted |
| `ConduitMcp.Discover` | `server/discover` result construction |
| `ConduitMcp.MRTR` | `InputRequests` builders, capability gating, response assembly |
| `ConduitMcp.MRTR.State` | AEAD seal/unseal of `requestState` |
| `ConduitMcp.Subscriptions` | Subscription registry and notification dispatch |
| `ConduitMcp.Subscriptions.Stream` | Per-subscription SSE stream process |
| `ConduitMcp.Plugs.HeaderValidation` | `Mcp-Method`/`Mcp-Name`/`Mcp-Param-*` validation |
| `ConduitMcp.Ext.Tasks` | Tasks extension API |
| `ConduitMcp.Ext.Tasks.Store` | Extension store behaviour |
| `ConduitMcp.Ext.Tasks.EtsStore` | Reference implementation |
| `ConduitMcp.Ext.Tasks.Janitor` | TTL expiry |

**Decomposed:** `handler.ex` (690 lines, currently doing routing, validation,
telemetry, cancellation, and four subsystems) splits into the era routers plus
the four method modules. Telemetry and cancellation move into one wrapper so
they are not reimplemented per era. This is targeted improvement to code the
change already touches, not opportunistic refactoring.

**Unchanged and shared by both eras:** schema validation, component
resolution, the DSL core, OAuth plugs, origin validation, rate limiting,
PromEx, `sse.ex`.

## Modern protocol surface

### server/discover

Mandatory, era-exempt. Built from the `__capabilities__/0` the DSL already
generates, so DSL users get it with no code changes.

```json
{
  "resultType": "complete",
  "supportedVersions": ["2026-07-28", "2025-11-25", "2025-06-18"],
  "capabilities": { "tools": {}, "resources": {}, "extensions": {} },
  "instructions": "...",
  "ttlMs": 3600000,
  "cacheScope": "private",
  "_meta": { "io.modelcontextprotocol/serverInfo": { "name": "...", "version": "..." } }
}
```

### Version negotiation

No handshake. Unsupported version returns HTTP `400` with
`UnsupportedProtocolVersionError` `-32022` and
`data: {"supported": [...], "requested": "..."}`. Because legacy support is
retained, an `initialize` request is served normally and the spec's
"name your versions in the initialize error" clause never applies.

### Header validation

Modern requests only. `MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name`
must be present and equal to their body counterparts. `Mcp-Name` and
`Mcp-Param-*` values are decoded from the `=?base64?<b64>?=` sentinel before
comparison; integers compare numerically (`42` equals `42.0`). Any failure is
HTTP `400` with `HeaderMismatch` `-32020`.

`Mcp-Param-*` headers are validated against tool parameters annotated with
`x-mcp-header`, declared in the DSL:

```elixir
tool "execute_sql" do
  param :region, :string, header: "Region"
  param :query, :string
end
```

The spec's static-reachability constraint — the property must be reachable
from the schema root through a chain consisting solely of `properties` keys,
never through `items`, `oneOf`/`anyOf`/`allOf`/`not`, `if`/`then`/`else`, or
`$ref` — is enforced **at compile time**. A violation is a build error rather
than a tool every conforming client silently drops from `tools/list`.

### MRTR

`Handler.Tools`, `Handler.Resources`, and `Handler.Prompts` accept a new
return value. These are the only three methods on which the spec permits
`InputRequiredResult`.

```elixir
def handle_tool_call(conn, "deploy", args) do
  case args["confirmed"] do
    nil ->
      {:input_required,
       %{"approval" => ConduitMcp.MRTR.elicit("Approve deploy?", schema)},
       %{step: :awaiting_approval, target: args["target"]}}

    _ ->
      {:ok, do_deploy(args)}
  end
end
```

On retry the library unseals `requestState`, and the handler receives
`params["inputResponses"]` alongside the restored term.

`ConduitMcp.MRTR` provides `elicit/2`, `sample/2` (`@deprecated`), and
`list_roots/0` (`@deprecated`). Each input request is gated against
`ctx.client_capabilities`: the spec forbids sending an input request the
client did not declare support for.

### subscriptions/listen

This is net-new infrastructure. The library currently has **no notification
delivery path at all** — `sse.ex` only runs a keep-alive loop, and
`handle_subscribe_resource/2` is a bare callback whose result is never used to
push anything.

`ConduitMcp.Subscriptions` is a `Registry` mapping subscription ID to its
owning stream process. The response to `subscriptions/listen` is a chunked SSE
stream that:

- emits `notifications/subscriptions/acknowledged` first, always, echoing only
  the filter subset the server honors;
- tags every message with `io.modelcontextprotocol/subscriptionId` in `_meta`,
  the value being the JSON-RPC id of the `subscriptions/listen` request;
- emits `:\r\n` SSE comments as keep-alives;
- sets `X-Accel-Buffering: no`;
- sends the empty graceful-closure result before server-initiated teardown.

Client disconnect is cancellation. Supported filter keys:
`toolsListChanged`, `promptsListChanged`, `resourcesListChanged`,
`resourceSubscriptions`, plus `tasks` when `Ext.Tasks` is enabled.

Public API for servers to push:

```elixir
ConduitMcp.notify_tools_changed()
ConduitMcp.notify_prompts_changed()
ConduitMcp.notify_resources_changed()
ConduitMcp.notify_resource_updated(uri)
```

The registry is node-local. Multi-node fan-out is documented as: broadcast on
your own PubSub, call these functions on each node.

### Logging

`logging/setLevel` does not exist on the modern path. Level comes from
`_meta["io.modelcontextprotocol/logLevel"]` per request, and
`notifications/message` is emitted **only** for requests that included that
field — a hard MUST NOT otherwise.

### Removed on the modern path

`initialize`, `notifications/initialized`, `ping`, `logging/setLevel`,
`resources/subscribe`, `resources/unsubscribe`,
`notifications/roots/list_changed`, GET and DELETE on the MCP endpoint (both
answer `405`), `Mcp-Session-Id` (ignored, never minted), `Last-Event-ID`
(ignored).

### Results

Every modern result carries `resultType: "complete"`. Results from
`tools/list`, `prompts/list`, `resources/list`, `resources/read`, and
`resources/templates/list` additionally carry `ttlMs` and `cacheScope`,
defaulting to `60_000` and `"private"`:

```elixir
config :conduit_mcp, cache_ttl_ms: 60_000, cache_scope: :private
```

overridable per component in the DSL. `tools/list` returns tools in
declaration order, stable across calls, for client-side cache hits.

## Tasks

### Risk

The [`ext-tasks` repo](https://github.com/modelcontextprotocol/ext-tasks)
README states it is "an **experimental** extension… **not** an official
extension and may change significantly or be discontinued," and is still
"working towards implementing the changes described in SEP-2663" — although
`modelcontextprotocol.io/extensions/tasks` presents it as settled. The two
already conflict: `ext-tasks` documents `-32003` for
`MissingRequiredClientCapability`, which the `2026-07-28` changelog renumbered
to `-32021`.

Consequences: `Ext.Tasks` ships behind explicit opt-in, its moduledocs mark it
experimental and unstable, and where the extension and core spec disagree the
core spec wins (we emit `-32021`).

### ConduitMcp.Tasks — frozen, legacy only

Serves `tasks/get`, `tasks/cancel`, `tasks/result`, and `tasks/list` to legacy
clients. The 0.10.1 owner scoping, `Tasks.Store`, `EtsStore`, and `Janitor` are
unchanged. Existing store implementations keep compiling untouched. No new
features; this subsystem is deleted when the legacy era is.

### ConduitMcp.Ext.Tasks — new

Own store behaviour: `create/2`, `get/2`, `update/3`, `cancel/2`,
`put_status/3`. Record fields: `task_id`, `status`, `status_message`,
`created_at`, `last_updated_at`, `ttl_ms`, `poll_interval_ms`,
`input_requests`, `input_responses`, `result`, `error`, `owner`.

There is deliberately **no `list/2`**: the absence of enumeration is a stated
security property of the extension. Task IDs are 32 bytes from
`:crypto.strong_rand_bytes/1`, url-safe Base64 without padding, because the
extension treats them as bearer tokens. Owner scoping is retained as defense
in depth — it is strictly stronger than the extension's floor and the library
already implements it.

Statuses: `working`, `input_required`, `completed`, `failed`, `cancelled`. The
last three are terminal.

Routes:

- `tasks/get` — polling read; terminal states embed `result` or `error`.
- `tasks/update` — accepts partial `inputResponses`; empty ack; the task
  returns to `working` once every outstanding key is satisfied.
- `tasks/cancel` — cooperative; empty ack; the task may still reach a
  non-`cancelled` terminal status.

A tool opts in by returning `{:task, attrs}`. The handler emits
`CreateTaskResult` with `resultType: "task"` only if the client declared
`io.modelcontextprotocol/tasks` in its per-request capability extensions;
otherwise `-32021` with the required capability in `data`. Task-augmented
execution applies to `tools/call` only. The task is durably stored before the
response is sent.

`notifications/tasks` is delivered through the `subscriptions/listen` filter
and carries the full task state.

`examples/oban_tasks_server/` and `guides/oban_tasks.md` port to `Ext.Tasks`.
The legacy Oban store remains as a frozen reference for `2025-11-25`
deployments.

## Sessions

The session subsystem survives intact and becomes **legacy-only**.
`Mcp-Session-Id` is minted, echoed, and validated on the legacy path exactly
as today. On the modern path it is ignored and never minted, and GET/DELETE on
the MCP endpoint answer `405`.

`ConduitMcp.Session`, the ETS store, the Redis/Postgres/Mnesia example stores,
and `Session.Janitor` are unchanged. `guides/multi_node_sessions.md` gains a
banner scoping it to the legacy era plus a section on the modern replacement:
server-minted opaque handles passed as ordinary tool arguments (SEP-2567).

## Errors

New in `ConduitMcp.Errors`:

| Function | Code | Meaning |
|---|---|---|
| `header_mismatch/0` | `-32020` | Header/body mismatch or missing required header |
| `missing_required_client_capability/0` | `-32021` | Client lacks a capability the request requires |
| `unsupported_protocol_version/0` | `-32022` | Requested version not implemented |

`resource_not_found` becomes era-dependent — `-32002` legacy, `-32602` modern
— and therefore moves out of `Errors` into the two `Protocol` shapers, since
one constant can no longer be correct for both eras.

Existing `task_not_ready/0` `-32004` remains valid: the spec grandfathers
`-32000..-32019` as implementation-defined.

## Security

`requestState` is the security core of this release. The spec requires servers
to treat it as attacker-controlled input.

`ConduitMcp.MRTR.State` uses AES-256-GCM via
`:crypto.crypto_one_time_aead/7` with a fresh 96-bit IV per seal. The key comes
from a required `:mrtr_secret` config value, validated as exactly 32 bytes at
application boot; a server that returns `{:input_required, …}` without it
fails fast rather than emitting unprotected state.

The sealed payload binds all three replay defenses the spec asks for:

- the authenticated principal — state presented by a different principal is
  rejected;
- an expiry, defaulting to 5 minutes;
- a SHA-256 digest of the originating method and its salient parameters —
  state presented on a different request is rejected.

Additional data (AAD) binds the protocol version and method.

Any verification failure returns a flat `-32602` disclosing nothing about
which check failed. `requestState` is never logged.

Replay is **bounded, not eliminated**. Single-use redemption requires
server-side storage; the spec makes this the implementer's responsibility and
the guide documents it rather than pretending otherwise.

Header validation is itself a security control: it prevents split-brain
between an intermediary routing on headers and the server executing on the
body.

## Testing

- **Era classification truth table** — every combination of `_meta` presence,
  method, and session header.
- **Conformance matrix** — every method exercised against both eras,
  asserting the correct method set is available and the correct error is
  returned for methods removed from that era.
- **Property tests** (`stream_data`, already a dependency) — round-trip of the
  `=?base64?…?=` sentinel; header/body equality including numeric comparison.
- **MRTR tamper tests** — flipped ciphertext bit, wrong principal, expired
  state, mismatched method digest; each must be rejected, and the error must
  be identical across all four so it leaks nothing.
- **Subscription tests** — acknowledgment ordering, filter subsetting,
  `subscriptionId` tagging, graceful closure, disconnect cleanup, registry
  leak-freedom after abnormal termination.
- **Compile-time tests** — invalid `x-mcp-header` annotations must fail the
  build.
- **Golden fixtures** — generated from the official `2026-07-28` `schema.json`
  into the existing `test/fixtures/`.

## Migration

Existing servers require **no changes**. They serve legacy clients as before
and gain modern core-method support automatically, because `server/discover`,
`resultType`, and cache hints all derive from what the DSL already knows.

Opt-in: `x-mcp-header` annotations, `{:input_required, …}` returns,
`Ext.Tasks`, cache overrides, the `notify_*` functions.

Breaking for direct users of:

- `ConduitMcp.Client` — rewritten as MRTR input-request builders; the old
  server-initiated request builders describe a pattern the modern era forbids.
- `ConduitMcp.Tasks` — frozen and legacy-only; modern clients need
  `ConduitMcp.Ext.Tasks`.
- `ConduitMcp.Errors.resource_not_found/0` — removed in favor of era-aware
  shaping.

New required config when MRTR is used: `:mrtr_secret`.

## Minor conformance items

Small, independent, and in scope for 0.11.0.

**OpenTelemetry trace context (SEP-414).** `traceparent`, `tracestate`, and
`baggage` are conventional `_meta` keys. `Ctx` carries them, and the telemetry
metadata already emitted by the request wrapper includes them so users can
bridge to their own tracer. The library does not take an OTel dependency.

**JSON Schema 2020-12 loosening (SEP-2106).** Validation is NimbleOptions-based
and driven by the DSL's own `param`/`arg` declarations, not a general JSON
Schema validator, so the blast radius is small. Three concrete changes:
`structuredContent` must accept any JSON value rather than only an object; the
schemas the DSL emits must be valid 2020-12; and a user-supplied raw schema
must not be rejected for carrying keywords the converter does not itself
understand. Full `$ref` resolution with composition-keyword resource bounds is
a client-side obligation and is not implemented here.

**`notifications/elicitation/complete` and `elicitationId` removal.** No work.
The library never implemented either — both were added in `2025-11-25` and
ConduitMCP does not reference them.

**OAuth changes: out of scope, by inspection.** All four OAuth minor changes in
this revision — RFC 9207 `iss` validation, `application_type` in Dynamic Client
Registration, issuer-bound client credentials, and Client ID Metadata Documents
— are obligations of MCP *clients* and *authorization servers*. ConduitMCP's
OAuth surface is resource-server only: `OAuth.ResourceMetadata` emits RFC 9728
Protected Resource Metadata, and `OAuth.KeyProvider` validates bearer tokens
against a JWKS. The library performs no client registration and redeems no
authorization codes, so none of the four apply. `authentication.md` gains a note
recording this, so the question is not re-litigated at the next revision.
